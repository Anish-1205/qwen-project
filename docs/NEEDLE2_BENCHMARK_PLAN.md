# Needle2 Intent-Routing Benchmark Plan

This document preserves the initial measurement brief for the
`needle2-intent-performance` branch. Paths and baseline observations describe
the pre-refactor implementation and should be reverified before new benchmark
runs.

## Objective

Evaluate the existing hybrid classifier against Needle2-only intent routing,
then retain the approach that produces the stronger measured routing results.

| Latency — Tool execution latency and slow-tool percentiles | `tools/manager.py::ToolManager.execute` at `definition.function(**arguments)`; tools include local file/directory/spreadsheet/calculator/random operations and network-backed weather, currency, search, and fetch — results are logged but durations are not — `MEASURE REQUIRED` | `BASELINE FIRST — TARGET AFTER MEASUREMENT`; establish per-tool p50/p95/p99 and timeout/failure budgets rather than one mixed target | Time only the registered function invocation; emit tool name, provenance, success/error code, timeout status, result size, and duration; aggregate percentiles per tool and separate local from network-backed tools. |

| Token/Memory — Prompt input and output tokens per Qwen call | `orchestrator.py::generate_reply` has exact `inputs["input_ids"]` and sliced `new_tokens`, but counts are not logged; configured maxima are 300/450 reply tokens, 120 router tokens, and 200 summary tokens depending on entrypoint/path — `MEASURE REQUIRED` | `BASELINE FIRST — TARGET AFTER MEASUREMENT`; report distributions by call purpose and context bucket, with zero unexplained token-count gaps | Record input token count, generated token count, requested `max_new_tokens`, actual stop reason, and call-purpose enum directly in `generate_reply`. |
| Token/Memory — Routing/control-plane and tool-call token cost | Semantic intent, tool-call generation/correction, memory extraction, and context summarization all reuse `ConversationOrchestrator.generate_reply`; no purpose-tagged accounting exists — `MEASURE REQUIRED` | Control-plane tokens `< 20% of tokens processed per successful turn`; if exceeded, reduce by 20% from measured baseline while preserving routing/tool success rates | Propagate a `call_purpose` label into `generate_reply`; sum input/output tokens for intent, tool generation, correction, summary, and memory extraction separately from final-answer tokens. |
| Token/Memory — Tokens processed before useful work and per successful turn | `process_turn` may invoke semantic routing before answer/tool work; tool turns can invoke Qwen repeatedly; memory writes invoke an additional extraction call after the answer — no per-turn token/model-call ledger exists — `MEASURE REQUIRED` | `BASELINE FIRST — TARGET AFTER MEASUREMENT`; reduce pre-tool/pre-answer tokens by 20% if they exceed 25% of successful-turn tokens | Maintain a turn-local ledger of every Qwen call’s purpose and token counts; snapshot cumulative tokens at first tool execution/final-answer generation and at successful turn completion. |
| Token/Memory — Multi-turn context growth and compression cost | `webapp.py::SessionState.messages` and `chat.py::messages` grow each turn; `orchestrator.py::process_turn` checks `count_tokens` against `max_context_tokens=1500`, then `compress_context` retains two recent turns in `chat.py` while the web app uses the constructor default of two; compression itself invokes Qwen — only post-compression token count is logged — `MEASURE REQUIRED` | Keep prompts within the configured 1500-token application budget where compression is enabled; compression p95 and added tokens require baseline before further target setting | Record message count, role-wise characters/tokens, pre/post-compression tokens, summarized tokens, retained turns, summary-generation latency/tokens, and compression frequency per session. |
| Token/Memory — Repeated/duplicated context and system/tool-schema overhead | `build_system_prompt` injects memory/document material; `generate_tool_aware_reply` appends safety/policy prompts, Qwen schemas, assistant/tool messages, and `_render_tool_ledger`; `count_tokens` repeatedly renders/tokenizes the full prompt — no component token attribution exists — `MEASURE REQUIRED` | Duplicated or repeated prompt tokens `< 5% of input tokens`; system + schema + ledger overhead must be baselined by tool path | Tokenize prompt components independently, hash normalized blocks to detect duplicates, and record tokens for base system prompt, history, memory, documents, tool policies, schemas, arguments, results, and ledger. |
| Token/Memory — Qwen prefill throughput, decode throughput, and total TPS | `orchestrator.py::generate_reply` provides input/output tensors but no synchronized stage timing; current blocking generation conflates prefill and decode — `MEASURE REQUIRED` | `BASELINE FIRST — TARGET AFTER MEASUREMENT`; publish tokens/s for short, medium, long, and near-1500-token prompts with fixed output lengths | Combine TTFT with input-token count for prefill throughput; combine post-first-token duration with decode-token count for decode throughput; record total processed tokens divided by synchronized inference duration. |
| Token/Memory — Context-length impact on latency and VRAM | Compression budget is `1500` tokens in `chat.py`; `ConversationOrchestrator` defaults to `1500` and webapp does not override it; no context-sweep benchmark or memory correlation exists — `MEASURE REQUIRED` | `BASELINE FIRST — TARGET AFTER MEASUREMENT`; benchmark fixed generations at short, medium, long, and near-1500-token inputs and report scaling curves | Run identical warm inference cases at fixed token buckets and fixed output length; record TTFT, ITL, prefill/decode TPS, allocated/reserved/peak CUDA memory, and system RAM for each bucket. |
| Token/Memory — VRAM idle, active, peak, and GPU memory utilization | Qwen loads in 4-bit NF4 with bfloat16 compute and `device_map="auto"` in `chat.py`, `infer.py::main`, and `webapp.py::_initialize_app`; no CUDA allocator or GPU utilization telemetry exists — `MEASURE REQUIRED` | `BASELINE FIRST — TARGET AFTER MEASUREMENT`; zero OOMs at the configured context/output limits and stable warm-call peak for identical workloads | After load and around each synchronized generation, record `torch.cuda.memory_allocated`, `memory_reserved`, `max_memory_allocated`, device identity, and process/GPU memory utilization; reset peak stats per call. |
| Token/Memory — KV-cache memory and growth | `model.generate` uses Transformers’ generation defaults and passes no explicit `use_cache`; no cache object, cache size, or per-step allocation is observed — `MEASURE REQUIRED` | `BASELINE FIRST — TARGET AFTER MEASUREMENT`; KV-cache growth must be monotonic with active sequence length and released after each completed call | Record effective `model.generation_config.use_cache`, prompt/output sequence lengths, cache implementation if exposed, and CUDA allocated-memory deltas after prefill and during decode; verify post-call reclamation over repeated turns. |
| Token/Memory — System RAM, CPU/GPU utilization, and CPU↔GPU transfer overhead | CPU embedding model is created in `memory_core.py::OfflineMemoryManager.__init__`; tokenization, SQLite, validation, document routing/retrieval, and embeddings run on CPU, while `generate_reply` moves tokenizer output to `self.model.device`; no resource sampling exists — `MEASURE REQUIRED` | `BASELINE FIRST — TARGET AFTER MEASUREMENT`; sustained CPU/GPU starvation and utilization gaps must be correlated with stage timings | Sample process RSS, CPU utilization, GPU utilization, and GPU memory utilization during each stage; separately time `.to(self.model.device)` and synchronized generation boundaries to expose transfer/synchronization overhead. |
| Token/Memory — Model/runtime initialization, reload/unload, and memory leak behavior | Each entrypoint (`chat.py`, `infer.py`, `webapp.py`) independently initializes Qwen, embedding model, and document index once per process; no unload path is present, and webapp guards `_initialize_app` with `init_started`; repeated-process and long-session memory behavior is unmeasured — `MEASURE REQUIRED` | Exactly one Qwen and one embedding-model initialization per process; no statistically significant monotonic RSS/VRAM growth across a fixed 100-turn warm workload | Count initialization calls and process IDs; record model object/device identity, load/unload events, and RSS/CUDA allocated/reserved after each fixed repeated turn plus post-GC steady state. |
| Routing/Fallback — Qwen calls per user turn and calls before useful work | `process_turn` can call Qwen for semantic intent, context summary, answer/tool generation, tool corrections/regenerations/finalization, and post-answer memory extraction; tool loop is bounded by `MAX_TOOL_CALLS_PER_TURN`, but no unified per-turn model-call count exists — `MEASURE REQUIRED` | Non-tool deterministic turn: one Qwen call; tool turn: baseline required by tool count; turns with more than one pre-work Qwen call `< 10%` unless a logged recovery branch requires it | Increment per-turn counters in `generate_reply`, labeled by purpose and generation round; record count at first useful work and completion, plus cumulative latency/tokens. |
| Routing/Fallback — Semantic routing frequency and avoidable/duplicate routing | `classify_intent` always runs `DeterministicIntentRouter.analyze` and invokes `IntentClassifier.classify` only when deterministic evidence is incomplete; no frequency or duplicate-input metric exists — `MEASURE REQUIRED` | Semantic Qwen routing on `< 30%` of benchmark turns after workload baseline, with no routing-accuracy regression; duplicate semantic calls for the same decision `0` | Count deterministic-complete versus semantic-required decisions, hash turn input plus recent-context slice, and flag repeated identical classifications within a turn/session. |
| Routing/Fallback — Intent repair and legacy-fallback frequency | `intent_classifier.py::classify` parses first output, performs one repair generation on any exception, then returns `IntentDecision.legacy_fallback`; `last_used_fallback` and `last_error` exist but are not aggregated — `MEASURE REQUIRED` | Initial classifier validity `≥ 99%`; repair frequency `< 1%`; legacy fallback `< 0.1%` on a labeled routing benchmark | Increment counters for initial parse success, repair attempted/succeeded, legacy fallback, and error category; attach first/repair latency and token cost without logging sensitive prompt content. |
| Routing/Fallback — Tool routing and no-tool/tool misclassification rate | `DeterministicIntentRouter` plus semantic classifier sets `IntentDecision.tool_use`; `process_turn` either enters `generate_tool_aware_reply` or directly answers; existing tests cover cases, but production correctness rates are absent — `MEASURE REQUIRED` | Wrong-tool and missed-tool rates each `< 1%` on a labeled representative benchmark; production rate remains `MEASURE REQUIRED` without labels | Record predicted `tool_use`, deterministic/semantic source, expected outcome in benchmark fixtures, actual tool names executed, and confusion-matrix counters. |
| Routing/Fallback — Malformed tool-call and regeneration frequency | `ToolManager.parse_tool_calls` emits `__invalid_tool_call__` for malformed/incomplete JSON; `generate_tool_aware_reply` may request a bounded correction or regenerate after failures/tool transitions — logs expose rounds but not aggregate rates — `MEASURE REQUIRED` | Malformed tool calls `< 1%`; correction/regeneration `< 2%` of tool turns on the benchmark suite | Count parse outcomes by malformed JSON, incomplete tag, missing/long name, invalid argument container, no-call, and valid call; associate each with regeneration count, added latency, and added tokens. |
| Routing/Fallback — Tool failure, retry, fallback-loop, and budget-exhaustion rates | `generate_tool_aware_reply` tracks `attempted`, `last_call_round_failed`, `correction_used`, outstanding required tools, deferred transitions, and budget exhaustion; special fallback exists for missing `TAVILY_API_KEY`; no aggregate telemetry exists — `MEASURE REQUIRED` | Fallback loops `0`; tool-budget exhaustion `< 0.5%`; retry success and failure rates require baseline by tool/error code | Emit one event per branch with reason enum, attempt/generation round, tool, error code, outstanding tools, budget remaining, terminal response type, and cumulative retry/fallback latency. |
| Routing/Fallback — Routing/control-plane share of total latency | Relevant paths are `classify_intent`, memory/document routing and retrieval, `generate_tool_aware_reply` tool-generation rounds, corrections, parsing, validation, and memory-extraction routing; timings are absent — `MEASURE REQUIRED` | Control-plane work `< 20% of end-to-end latency` at p95 excluding unavoidable external tool execution; otherwise reduce by 20% from baseline | Sum purpose-tagged stage durations per turn and divide by endpoint duration; report deterministic routing, semantic routing, retrieval, tool generation, validation, retry, and fallback shares independently. |
| Schema/Tooling — FastAPI/Pydantic request validation latency and rejection rate | `webapp.py::ChatRequest(BaseModel)` validates `message` length 1–20000 and optional `session_id` before `chat`; FastAPI handles failures before endpoint entry and no validation telemetry exists — `MEASURE REQUIRED` | p95 request-model validation `< 1 ms`; schema rejection rate and payload-size relationship require baseline | Add lightweight middleware timestamps around request parsing/validation and count HTTP 422 outcomes by field/error type and request size. |
| Schema/Tooling — Tool JSON parsing and argument-parsing latency | `tools/manager.py::parse_tool_calls` performs tag regex matching, strict `json.loads`, optional nested argument-string parsing, and call-ID/name bounds — `MEASURE REQUIRED` | p95 `< 1 ms` for normal calls and `< 5 ms` at configured maximum argument/result sizes | Time regex extraction, outer JSON parse, nested argument parse, and `ToolCall` construction independently; record input characters, call count, malformed reason, and CPU time. |
| Schema/Tooling — Custom JSON-schema validation latency and rejection rate | `tools/manager.py::ToolManager._validate` recursively handles `oneOf`, object, array, string, numeric, enum, required/default/additional-property rules; this repository uses this custom validator rather than Pydantic for tool arguments — `MEASURE REQUIRED` | p95 `< 2 ms` for ordinary schemas and `< 5 ms` for maximum-size arrays; schema rejection rate `< 1%` on valid-tool benchmark prompts | Time `_validate` independently from model inference and tool execution; record tool/schema, recursion/node count, argument size, success, rejection path/category, and CPU time. |
| Schema/Tooling — Argument normalization, sanitization, and execution-guard cost | `ToolManager._normalize_arguments`; `tools/common.py::resolve_local_path`, `resolve_file`, `validate_zip_archive`, and `validate_public_url`; `orchestrator.py` current-turn URL guard; `logging_utils.py::sanitize_tool_log_payload` — `MEASURE REQUIRED` | p95 local normalization/guards `< 2 ms`; DNS-dependent URL validation must be reported separately from deterministic checks | Add timers around normalization, path/file/archive guards, URL syntax and DNS resolution separately, current-turn URL authorization, and log sanitization; preserve all validation behavior. |

| Schema/Tooling — Logging/telemetry overhead | `logging_utils.py::setup_debug_logger` uses synchronous `RotatingFileHandler`; `capture_prints` redirects stdout/stderr; `sanitize_tool_log_payload` recursively cleans and JSON-serializes payloads; detailed per-turn logging occurs throughout `process_turn` and tool loops — `MEASURE REQUIRED` | Logging/sanitization p95 `< 1% of end-to-end latency` and no more than 5% throughput reduction in an identical on/off benchmark | Time formatter, payload sanitization, handler emission, and flush operations; compare fixed workloads with normal logging versus a null handler while preserving identical application behavior. |
